# API, Tool, and Command Contracts v1

This is the normative interface design. Gate II implements health/catalogue, discovery/creation/deletion, operation lookup, case/evidence/history reads and fixture preview/confirmation. Gate III implements investigation start/status/results. Gate IV adds draft generation/retry/edit/review, historical draft inspection, advice decisions and explicit lifecycle commands. Entity fields/invariants are in [data-model.md](../data-model.md). Strict Pydantic boundary models generate OpenAPI. Reject unknown request fields/coercion. Public prefix: `/api/v1`; same-origin loopback only.

## Common types and requests

- `Id`: UUID string; `SourceId`: stable catalogue source string; `Instant`: aware RFC3339 UTC string; `Revision`: nonnegative integer; `Hash`: lowercase SHA-256 hex string.
- `Money`: `{currency:"INR", minor_units:string}`; minor_units matches `^-?(0|[1-9][0-9]*)$`. Values on source records may be unknown/invalid; do not encode unknown as zero. Derived overpayment may be negative.
- `Action`: FOLLOW_UP | WAIT | VERIFY_PAYMENT | CLOSE. `AttemptStatus`: RUNNING | COMPLETE | LIMITED | INCOMPLETE. `Freshness`: CURRENT | EVIDENCE_CHANGED | TIME_EXPIRED | SUPERSEDED | INCOMPLETE. A running newer attempt additionally blocks approval/closure.
- A mutation receives `schema_version:"1"`, `operation_id:Id`, and its exact typed payload. Case mutations also receive `expected_case_revision:Revision`. Approval includes expected review_epoch and exact draft hash. A UI retry after lost response retains the same ID/payload.
- Mutations require `Content-Type: application/json` and `X-PromiseKeeper-Request: 1`. Check loopback Host and allowlisted Origin when present; no wildcard CORS. These controls do not claim authentication. Error responses never echo secrets or raw provider responses.
- Hash canonical JSON with sorted keys and UTF-8, preserving exact text values. Do not normalize text/recipient after approval. Hash format/version is recorded. Idempotency lookup precedes revision/eligibility checks.
- Case, evidence-version, history, scenario-event and investigation routes require `demonstration_id:Id` as a query parameter to bind the selected-copy scope. Foreign-copy IDs return 404. Case IDs alone never select another copy implicitly.
- Mutation responses use `{schema_version:"1", receipt:Receipt, ...typed result fields}`. Operation lookup returns that same envelope. Deletion retains content-free identities for prior operation IDs: their subsequent replay/lookup returns a `DELETED` receipt, never recreates a copy or re-executes a command, and changed payloads still conflict. Only copy/operation identity, operation type, request hash and commit time survive in those tombstones.

## Operations

| Method/path | Payload beyond common fields | Response and effects |
| --- | --- | --- |
| GET `/health` | None | Readiness, schema/catalogue version, agent_mode STUB/LIVE, safe configuration status. No credentials. Recovery/ownership completes before ready=true. |
| GET `/catalogue` | None | Approved catalogue/version, baseline/variant/event IDs, update definitions and registered clock events. Obtain a case-bound confirmation hash from the preview endpoint below. No arbitrary creation/import. |
| GET `/demonstrations` | None | `{schema_version:"1", demonstrations:DemonstrationSummary[]}`; every persisted nondeleted copy, ordered by created_at then id. Read-only; never creates/reseeds a copy. |
| POST `/demonstrations` | catalogue_version:string, variant_id:string or null, clock_mode REFERENCE/REAL | 201 receipt plus demonstration_id. Fresh isolated copy with exactly three cases; server validates registered variant. No reseeding on restart. |
| GET `/demonstrations/{id}/cases` | None | Copy/mode/evaluation time plus three summaries: case/client/invoice/currency/due date/lifecycle, previous-investigation and review-required indicators. |
| GET `/cases/{id}` | None | CaseView below, current revision, complete source access, current/last-completed distinction. |
| GET `/evidence-versions/{id}` | None | Exact preserved original/version/provenance and availability, including historical sources; validate demonstration ownership. |
| GET `/cases/{id}/history` | cursor nullable, limit integer 1–100 (default 50) | Ordered immutable events, referenced results/reviews and next cursor. Ordering is sequence, not browser timestamps. |
| POST `/cases/{id}/investigations` | retry_of:Id or null | 202 receipt, investigation_id, snapshot_id, evaluation_at, deadline_at. Require OPEN case. Replay known receipt before capacity rejection; reserve global slot before persisted start/invalidation. Rollback/terminal outcome releases slot. |
| GET `/investigations/{id}` | None | Attempt status, snapshot/version refs, limitations/error, result/action or null, independent draft status, safe progress. |
| GET `/cases/{id}/scenario-events/{event_id}/preview` | None | ScenarioEventPreview below, including exact target/revision/evidence/clock changes and preview_hash. Only events registered for this case/variant; no mutation or authority change. |
| POST `/cases/{id}/scenario-events` | event_id:string, catalogue_version:string, confirmed_preview_hash:Hash | 200 committed receipt. Explicit confirmation of the case-bound preview; recheck version/target/revision/hash atomically. Replay known operation before revision/hash checks. Updates append immutable evidence/anchors and invalidate freshness/approval; no user verification flag or arbitrary payment body. |
| POST `/cases/{id}/draft-versions` | investigation_id:Id, parent_version_id:Id, exact_text:string (1–8000 chars), recipient:string | 201 new unapproved version, payload_hash, validation status/reasons. Preserve invalid financial wording as an unapproved draft for correction; no authority changes. Recipients must belong to the fictional case catalogue. |
| GET `/draft-versions/{id}` | demonstration_id:Id | `{schema_version:"1", draft_version:DraftVersion}` with the exact immutable saved text, recipient, invoice, result and validation context. Foreign-copy IDs return 404; inspection grants no review authority. |
| POST `/cases/{id}/draft-retries` | investigation_id:Id, failed_draft_attempt_id:Id, expected_draft_head:Id or null | 202 draft_attempt_id/receipt. Retry failed draft generation against the same current completed result, without rerunning investigation or overwriting a newer edit. Keep automatic-retry usage; fresh manual operation deadline at most 55 seconds. |
| GET `/draft-attempts/{id}` | None | RUNNING/READY/FAILED, draft_version_id or null, safe failure/retry information. No new recommendation. |
| POST `/cases/{id}/draft-reviews` | draft_version_id:Id, payload_hash:Hash, expected_review_epoch:Revision, decision APPROVE/REJECT | 200 committed review/receipt plus current validity. Approval eligibility rechecked atomically. Historical rejection is a recorded disposition only. |
| POST `/cases/{id}/dispositions` | investigation_id:Id, decision ACCEPT/REJECT, reason:string or null (max 1000 chars) | 200 advice disposition/receipt. Does not approve draft, close case, or change evidence. |
| POST `/cases/{id}/closure` | investigation_id:Id, confirmed_result_hash:Hash, confirm:true | 200 closure/receipt only for current eligible CLOSE. Review includes case/invoice/result and settlement sources. |
| POST `/cases/{id}/reopening` | confirm:true, reason:string or null | 200 reopening/event/receipt. Preserves closure and financial evidence. |
| GET `/operations/{operation_id}` | demonstration_id:Id | Durable receipt or 404 NOT_RECORDED. Resolve unknown outcome before new ID; 503 during unavailable recovery is not proof of failure. |
| POST `/demonstrations/{id}/deletion` | confirmed_demonstration_id:Id, confirm:true | 200 content-free deletion receipt. Purges only selected copy; no delete-all operation. Tombstone permits repeat replay. |

An owner-triggered investigation retry is a new start command/operation with `retry_of:Id` optionally identifying the incomplete predecessor. It does not reset or resume that attempt. This is the only additional allowed investigation-start field. Repeating a transport submission is not a new owner retry and retains its original operation ID.

`DemonstrationSummary` has id:Id, catalogue_version:string, created_at:Instant, clock_mode:REFERENCE|REAL, and selected_variant_id:string|null. Root-page discovery restores a valid browser selected_demonstration_id; without one, select the sole copy, show a chooser for multiple copies, or require an explicit create action for no copies. Creation selects the returned ID. A missing/deleted selection is cleared and the same discovery rule applies. A listing failure preserves the saved preference and shows a recoverable error, never an empty-list/create-success claim. Selection is local navigation, not a backend financial mutation; pending commands/receipts remain scoped to their original copy.

Each catalogue event includes `eligible_variant_ids:(string|null)[]`; null identifies the baseline copy. Filter fictional-update choices by the selected saved copy's `selected_variant_id`, case and clock mode. Eligibility lists describe registration only; preview and confirmation still revalidate current state on the server.

`ScenarioEventPreview` has schema_version:"1", catalogue_version:string, demonstration_id:Id, case_id:Id, event_id:string, expected_case_revision:Revision, evidence_changes:typed immutable catalogue records/anchor definitions, clock_change:{from:Instant,to:Instant}|null, and preview_hash:Hash. Hash all preceding fields using the common canonical JSON rule; exclude preview_hash itself. The confirmation POST uses exactly that revision/event/version/hash. If the current revision or proposed changes differ, require a new preview and confirmation. The service and both routes are Gate II dependencies of staged investigation/review tests; the fixture-update UI and closed-case lifecycle integration arrive in Gate IV.

## CaseView and result payload

`CaseView` contains schema_version, demonstration/case/client/invoice identifiers, lifecycle, case_revision, evidence_revision, review_epoch, current_draft_version_id or null, clock_mode, displayed evaluation_at, evidence versions/availability/completeness and payment verification_status, latest_completed_result or null, current_result or null, running_attempt or null, current draft/review/generation state, review_required reasons, and allowed_commands with blocking reason codes. Browser controls use server eligibility; every write rechecks it.

Case summaries expose the original invoice `due_text:string|null` for display separately from `due_at:Instant|null`, the exclusive overdue boundary. A midnight boundary on the following day must not be displayed as the original invoice due date.

`Result` contains investigation_id, snapshot_id/hash, original evaluation_at, status COMPLETE/LIMITED, financial facts with KNOWN/UNKNOWN and reasons, commitments with commitment_stable_id/key or explicit unresolved identity, claims, timeline source refs, contradictions, unresolved questions, one action, reason_code, deterministic explanation with source refs, concrete next_step, review_at (required for WAIT, otherwise null), and result_hash. WAIT review_at is the earliest future invoice-due boundary or expiry of an active, unfulfilled promise justifying waiting; reaching it requires review and does not imply FOLLOW_UP. A known contested remainder remains labeled recorded remainder; a VERIFY_PAYMENT result cannot contain a demand. INCOMPLETE returns result=null and a precise retry/review step.

New results use `findings_version:"deterministic-1"`. Code derives all contradictions, unresolved questions, financial issues, commitment issues and evidence observations before hashing and persistence. Financial and commitment issues contain `{code,detail,sources:string[],source_versions:SourceVersionRef[]}`, where each `SourceVersionRef` is `{source_id:string,evidence_version_id:Id}` naming the exact retained version. Preserve every material issue even on COMPLETE results and when it does not change the action. Case-summary financial issues may omit version references.

`EvidenceObservation` contains `{subject:"LEDGER"|"SOURCE",field:"availability"|"complete"|"content_present",value:availability-enum|boolean,snapshot_id:Id,snapshot_hash:Hash,source:SourceVersionRef|null}`. Every new result includes the captured ledger availability and completeness with null source. A non-AVAILABLE source has an exact-version availability observation; empty original content has `content_present:false`. Empty or unavailable content never gets a fabricated quote. Observations retain the investigation's snapshot identity.

Questions have one exact source span per `(field,source_id)`; contradictions have one source pair per `(kind,sorted source IDs)`. Issues deduplicate by `(code,sorted source IDs)`. Reject overflow rather than truncating: 4096 contradictions, 512 questions, 512 financial issues, 512 commitment issues and 128 observations. Earlier saved results remain readable with their original JSON and hash; reads do not insert the new fields or recompute findings. The UI labels their older findings profile and requests explicit reinvestigation.

`Receipt` contains operation_id, operation_type, target_id, committed_at, outcome and resulting case_revision when applicable. An investigation receipt acknowledges persisted start, not successful completion. A receipt cannot claim a saved decision before commit.

Gate IV mutation envelopes add `draft_version`, `draft_review`, `draft_attempt_id`, `disposition`, or `case_id`/`lifecycle` to their receipt as appropriate. Operation lookup returns the same typed envelope, including after a lost response. `CaseView` includes `draft`, `draft_reviews`, `draft_generation_attempt`, `no_draft_reason` and `owner_dispositions`; current eligibility includes edit/approve/reject/retry draft, disposition, close and reopen. Required initial draft intent commits with its completed recommendation; generation runs after commit, so restart can mark an interrupted draft step failed and offer explicit retry without losing the recommendation.

## Approval and draft validation

An APPROVE command must reference current_draft_version_id, the latest completed investigation, current evidence/time, exact draft version/recipient/invoice/hash, current review_epoch, and no running investigation. Revalidate inside BEGIN IMMEDIATE with review/event/receipt. An edit checks its parent against the current head, then atomically advances head, case_revision and review_epoch and invalidates approval. A new persisted investigation changes the epoch even if it later fails. After INCOMPLETE, fresh explicit approval of an earlier eligible current draft may use the new epoch; old review IDs remain invalidated. A newer edit, evidence change or superseding successful result still blocks the original version.

Initial drafts/explanations use templates with typed supported fact clauses. For this bounded English catalogue, approval validation uses a conservative allowed-clause grammar: factual clauses must match an allowed rendered fact/template alternative; nonfactual greeting/request/closing alternatives allow neutral wording changes such as Hello -> Hi. Unsupported or unrecognized financial clauses, altered amounts/currencies, fees/threats/invented bank instructions, and unresolved placeholders block approval with clause-specific reasons. Free edits may be saved unapproved; the editor can offer safe wording alternatives. Do not claim general natural-language factual verification from regex or model plausibility. The human still reviews the exact final message. No endpoint sends or labels it SENT.

## Read-only Investigator boundary

`read_snapshot({schema_version:"1", snapshot_id:Id, evidence_version_ids:Id[]})` returns only records in that immutable snapshot, their source IDs/original text, authority/availability/completeness metadata, original timestamps/timezones, approved commitment anchors (commitment_key, evidence_version_id, clause_start, clause_end), and integrity hash covering those anchors. Anchors identify clauses only; they supply no extracted amount/date, fulfillment or verification authority. No arbitrary path/URL/case query. The orchestrator selects the packet before calling the Investigator; there is no autonomous tool loop. Packet limit: 64 records, each at most 8000 Unicode code points, total at most 64000; an oversized registered fixture fails visibly, never silently truncates. Runtime deadlines include reading/validation.

Investigator input includes schema_version, investigation_id, snapshot_id/hash, packet and extraction prompt version. Output conforms to [investigator-output.schema.json](investigator-output.schema.json). It includes candidates only: no authoritative balance, action, deadline instant, verification, approval, or side-effect fields. Runtime checks enforce output snapshot identity, allowed IDs, exact source spans and supported candidate syntax/relationships. Date/money parsing and explicit attribution authority remain deterministic. Refusal/malformed/foreign-reference output produces a safe failure, not a fabricated empty successful extraction.

The production `candidate-only-1` policy narrows structural schema version 1: both `contradictions` and `unresolved` must be empty arrays for STUB and LIVE. The provider schema enforces zero items and runtime validation rejects violations. The general structural schema remains compatible for historical tools. The model extracts raw message candidates; the production findings service has no dependency on evaluation expectations or fixture oracles.

Contradiction categories describe direct source disagreements. `INVOICE_FACT` compares invoice records. `PAYMENT_CLAIM` compares a customer claim with an active ledger record only when an explicit transaction reference binds them. Conflicting active ledger records for the same explicit transaction use `OTHER_CANDIDATE`. Reversal and reversed records are excluded from those comparisons: a reversal changes settlement status later and does not itself contradict an earlier statement that payment occurred. Different references, a partial payment differing from an invoice total, arithmetic overpayment alone, formatting differences, identical duplicates and resolved authoritative corrections do not establish contradictions. Compare supported normalized facts without inventing values for unknown/invalid fields. These questions never verify a payment or change deterministic financial facts. An unresolved field must be missing, invalid or disputed on its exact cited source; an unresolved balance does not make every amount or currency unknown.

`ATTRIBUTION` means a verified payment's link to a particular anchored commitment. Current attribution questions require an active unfulfilled commitment and an actual unresolved eligible payment link; superseded commitments remain historical. Invoice allocation is a separate relationship and remains a deterministic financial finding. A source amount with invalid INR precision is preserved as text but cannot establish a normalized numeric disagreement; an exact-source `AMOUNT` question may identify that invalidity. A known currency disagreement does not make an equal numeric amount disputed. Invoice due-date gaps remain financial issues rather than promise/payment date questions. Extract stated temporal wording verbatim even when vague or unresolvable. An unresolved date question may coexist with that raw text; it never supplies a deadline instant. Null date text means no temporal expression was stated.

Temporal policy `deadline-by-1` permits a source-stated single leading `by` before an otherwise supported known commitment deadline. Preserve that original wording while retaining the bare expression's date-only IST boundary, explicit offset or required original timestamp anchor. Negation, approximation, unsupported suffixes, invalid dates and unanchored/vague expressions remain unresolved. Payment-day parsing stays strict: a deadline bound does not establish an actual payment day. Evaluation retains literal actual/expected fields and accepts only this narrowly verified commitment-deadline connector difference; other candidate fields remain exact. The temporal policy is recorded in evaluation identity.

Span offsets are zero-based Unicode code-point indexes with an exclusive end: require 0 <= start < end <= source length and exact equality of source[start:end] and quote. Amount/currency/date/reference token text must be supported by the cited span; speaker identity may use the original source's author metadata. Null means unknown, not zero or a guessed date. Reject duplicate candidate IDs or references outside the snapshot. A commitment candidate returns commitment_key:string|null from the supplied anchors. Bind only to the matching source-version anchor when the quote intersects exactly one catalogue commitment clause and all nonnull amount/currency/date tokens occur within both that clause and the quote. Null or ambiguous binding remains unresolved (VERIFY_PAYMENT if material); unknown/foreign provided keys are invalid output. Resolve explicit replacement references from supported source relationships to exact anchored identities; ambiguous message-only references remain unresolved. Persistent commitment identity is the preexisting anchor ID for (demonstration_id, evidence_version_id, commitment_key), independent of candidate IDs and selected quote offsets. FV-16's full-message and shorter valid quotes must preserve the same identity/link/action across investigations. Known deterministic evidence gaps may support a LIMITED/VERIFY_PAYMENT result with explicit missing extraction; never present skipped extraction as a successful full investigation.

## Errors and retry policy

Error envelope: `{schema_version:"1", error:{code:string, message:string, operation_id:Id|null, retryable:boolean, blocking_reasons:string[]}}`. Messages are plain-language and redacted.

| Status | Codes / meaning |
| --- | --- |
| 404 | NOT_FOUND, NOT_RECORDED; no cross-copy leakage. |
| 409 | REVISION_CONFLICT, OPERATION_PAYLOAD_MISMATCH, INVESTIGATION_RUNNING, CASE_CLOSED, STALE_RESULT, SUPERSEDED_RESULT, DRAFT_VERSION_CHANGED, REVIEW_EPOCH_CHANGED, INELIGIBLE_CLOSURE, PREVIEW_CHANGED. Refresh/review; never force overwrite. |
| 422 | INVALID_REQUEST, UNAPPROVED_CATALOGUE_ENTRY, INVALID_DRAFT, UNSUPPORTED_PAYLOAD. No automatic retry. Invalid financial fixture evidence is a domain review outcome, not silently rejected evidence. |
| 503 | INVESTIGATOR_BUSY, STORAGE_UNAVAILABLE, RECOVERY_IN_PROGRESS, CAPABILITY_UNAVAILABLE. Preserve view and receipt reconciliation. No false zero-payment/saved/success state. |

Each failed internal step has at most one automatic retry, transient conditions only, with persisted counts and global 55-second budget. Disable provider hidden retries. Invalid output/refusal is not retried as a hidden repair. API clients reconcile unknown commits using the same operation ID. Terminal attempts reject all late callbacks.
